# TRUTH: pipe-jq-sed-awk-pipeline-order-matters

## The single most important insight

You are converting a stream of JSON audit records into a canonical, sorted, deduplicated tab-separated file, and the four things you must do — severity filter, field projection, path-segment drop, and dedupe-plus-sort — are only correct in one order. Each stage strips information the next stage needs. If you flatten the JSON into `@tsv` **before** the severity filter runs, the string `"critical"` no longer sits under the JSON path `.severity`; it becomes an unlabeled column and your downstream filter has to guess which one. If you drop test paths **before** the TSV projection, your awk regex is looking at raw JSON where `$4` is a random word chopped by whitespace, not the value of `.path`. If you dedupe **before** you drop the test-path rows, the dedupe collapses rows that never should have survived, hiding the drop from you.

The naive shortcut is to reach for one big `jq -r 'select(.severity=="critical") | [.package,.version,.advisory.id,.path] | @tsv'` and then throw awk/sort at the tail; that shape is fine. The naive shortcut that actually bites you is to swap the awk stage and the sort stage, or to put `sort | uniq` before awk because sort "obviously comes last." Both produce a plausible non-empty file. Both fail the grader silently on either the row-set check or the ordering check. The correctness of this task is not in any single tool call — it is in the sequence.

## The ideal solve, step by step

1. **Filter by severity while the JSON is still JSON.** Run `jq -c 'select(.severity == "critical")' /workspace/input/audits.jsonl` as your first stage. You do this here, not later, because `.severity` is a named field only while the record is JSON; once you flatten to TSV the string `"critical"` becomes just another column and any downstream match against it has to know the column index and worry about substring hits. Filtering first also throws away roughly two thirds of the corpus (the info/low/moderate/high records and the ones missing `.severity` entirely), so every downstream stage runs on far less data.

2. **Project to a four-column TSV in the exact required order.** Chain `| jq -r '[.package, .version, .advisory.id, .path] | @tsv'` as your second stage. You use `@tsv` (not a hand-built `join("\t")`) because `@tsv` handles embedded tabs, newlines, and backslashes in string values by escaping them into `\t`, `\n`, and `\\` — a hand join would corrupt any field containing a literal tab and would silently produce a five-column row that later fails the per-row shape check. You emit the columns in the sequence the deliverable specifies: package, version, GHSA id, path. Getting that order wrong shifts every downstream sort key.

3. **Drop test-path rows with awk against the tab-split fourth field.** Chain `| gawk -F'\t' 'BEGIN{OFS="\t"} $4 !~ /(^|\/)(test|__tests__)(\/|$)/ {print}'` as your third stage. You set `-F'\t'` so awk splits on the tab byte exactly, not on runs of whitespace; that guarantees `$4` is the `.path` value even if some other field carries internal whitespace. The regex anchors on whole `/`-delimited segments — `(^|/)` before and `(/|$)` after — so a package literally named `latest-tests-runner` or a directory named `contest-runner` is not dropped by a naive `/test/` substring match. You do this stage after the TSV projection because before it, `$4` refers to an unrelated whitespace-delimited chunk of the raw JSON object.

4. **Dedupe and sort last, under a byte-order locale.** Chain `| sort -u -t $'\t' -k1,1 -k2,2 > /workspace/out/critical.tsv` as your fourth stage, and export `LC_ALL=C` before the pipeline runs. `sort -u` collapses byte-duplicate rows in a single pass — no separate `uniq` needed. `-t $'\t'` sets the field separator to the tab byte so `-k1,1 -k2,2` key on package then installed version and nothing else. `LC_ALL=C` forces byte-order comparison so `@angular/core` sorts before `axios` (byte `@` = 0x40 comes before byte `a` = 0x61), matching the grader's C-locale expectation. Any other locale reorders `@`, `-`, and `.` unpredictably and the ordering check fails.

## Traps that catch agents that are not thinking carefully

- **Trap: case-normalizing `.severity` "for safety".** A tempting hardening is to write `select((.severity // "") | ascii_downcase == "critical")` on the theory that some records will spell severity with a capital C. The corpus contains records whose `.severity` is `"Critical"` and `"CRITICAL"` deliberately — those are misfilings the deliverable expects you to drop, since the filter rule is literally "exactly the string `\"critical\"`". Case-normalizing turns those misfilings into false positives and blows the row-set check. Match the exact string, nothing more.

- **Trap: reaching for `sed '/test/d'` because the slot name says jq | sed | awk.** The bundle name promises a `sed` stage, but the correct pipeline has none — `sed` is the wrong tool here. `sed '/test/d'` deletes any line containing the substring `test` anywhere: it would drop the row for `typescript` (contains `test` inside `typescript`), it would drop `@types/node` (contains `test` inside `types`), and it would drop the row for `contest-runner` if such a package existed. Only awk with `-F'\t'` and a whole-segment anchored regex targeting `$4` is safe. If the bundle name misleads you into inserting `sed`, you have lost several legitimate survivors before the sort even runs.

- **Trap: sorting-and-deduping before dropping test paths.** `sort -u | awk '...'` looks equivalent to `awk '...' | sort -u` and runs faster on some inputs, but `-u` collapses byte-duplicate rows into one representative *before* awk sees them. If a test-path row and a non-test row happen to be byte-identical (same package, same version, same GHSA id, same path — which happens when the corpus records the same advisory once with a test dependency graph and once without), the dedupe keeps one and awk then removes it if that one happens to be the test-path copy. The failure is silent: the file exists, has the right shape, is sorted, and is quietly missing legitimate rows.

- **Trap: leaving `LC_ALL` unset and trusting the container locale.** The image likely has `en_US.UTF-8` or similar set. Under UTF-8 collation, `sort` folds case and reorders punctuation by Unicode collation weights, which puts `axios` before `@angular/core` and interleaves `@babel/core` with `body-parser` in surprising ways. The grader compares against a C-locale byte-order reference — the `@` sign is byte 0x40, alphabetics are 0x61+, so every `@`-scoped name must sort before every unscoped name. Exporting `LC_ALL=C` (or prefixing `LC_ALL=C sort ...` inline) is the only reliable fix; adding `-b` or `--ignore-leading-blanks` does not help.

- **Trap: using `awk` without `-F'\t'`.** Writing `awk '$4 !~ /(^|\/)(test|__tests__)(\/|$)/'` without setting the field separator splits on runs of whitespace. If a projected row is `chalk 4.1.0 GHSA-a7b8-c9d0-e1f2 node_modules/chalk`, awk sees four whitespace-delimited fields and things happen to work; but if any future audit record's package name gets a stray space, the column count shifts silently. Setting `-F'\t'` is a one-character insurance policy that guarantees column alignment matches the TSV your previous stage just emitted.

- **Trap: using `sort -k1 -k2` without the comma-bounded key ranges.** Writing `sort -k1 -k2` looks like it keys on fields 1 and 2, but `-k1` without an end field means "from field 1 to end of line" — the entire line becomes the primary key, and `-k2` is dead code. Two rows with the same package and version but different GHSA ids or paths then order by the whole-line comparison rather than by field-2 alone, producing an ordering that superficially looks right but silently diverges from the deliverable's `(field 1, field 2)` contract. Write `-k1,1 -k2,2` with the comma-bounded ranges so each key is exactly one field wide.
