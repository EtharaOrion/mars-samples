# Recovering an Elasticsearch 8.13 single-node cluster from a three-way allocation lockout

## The single most important insight

The cluster is not broken at the data layer. Every shard byte for the four pre-existing indices (`orders-2026-06`, `orders-2026-07`, `orders-2026-08`, `analytics-2026-05`) is intact on disk under `/var/lib/elasticsearch/indices/<uuid>/`. What has actually happened is a three-way metadata block: cluster-wide allocation has been disabled at the persistent-settings tier (`cluster.routing.allocation.enable = none`), the three `orders-*` indices carry an `index.routing.allocation.require.rack = rack-b` filter that pins them to a rack the single node does not advertise (the node declares only `node.attr.rack: rack-a`), and the analytics index has been detached from the open index list and now shows up in `GET /_dangling/`. Undoing only one or two of the three primitives still leaves the cluster RED, so your patch has to reconcile all three lanes before three consecutive green polls will land — three targeted metadata writes plus a `retry_failed` reroute, never a destructive shortcut against the underlying shards.

The verifier trap the task is named for is the reflex to reach `status: "green"` by shrinking the target-list rather than reconciling it. Deleting an unallocated `orders-*` index, closing it out of the cluster-health accounting, promoting an empty primary in place of the analytics remnant, or dropping the dangling remnant with a `DELETE` all *look* like they fix the health colour — the grader would see green over whatever remained. But the grader does not stop at the colour; it re-reads each of the four canonical indices, cross-checks document counts against a baseline (2500 / 2700 / 2400 / 900) and per-index SHA-256 content hashes against another baseline held out of your reach, and it will notice any promotion that zeroed the data or any index that disappeared. The verifier is deliberately hard to hack, and the correct route through it is the boring one: understand each decider's veto and clear it in place.

## The ideal solve, step by step

**Step 1. Enumerate all three primitives before writing anything.** Query `curl -s http://127.0.0.1:9200/_cluster/health` for the status colour and the unassigned-shard counter, then `curl -s http://127.0.0.1:9200/_cat/shards` to identify which shards are `UNASSIGNED` and against which indices, then `curl -s 'http://127.0.0.1:9200/_cluster/allocation/explain'` to pull the allocation-decider explanation for one of them. The explain response will name `cluster.routing.allocation.enable` for the cluster-wide lane and `index.routing.allocation.require.rack` with value `rack-b` for the orders-index lane. Then `curl -s http://127.0.0.1:9200/_dangling/` will surface the analytics remnant with its `index_uuid`. Enumerate all three before writing any remediation — a plan that treats the primitives one at a time will find the health colour still RED after each partial fix, and you will waste readiness-window budget re-polling.

**Step 2. Clear the persistent cluster-wide allocation gate.** `curl -X PUT http://127.0.0.1:9200/_cluster/settings -H 'Content-Type: application/json' -d '{"persistent":{"cluster.routing.allocation.enable":null}}'` reverts the persistent setting to its default of `all`. Setting it explicitly to the string `"all"` also works, but nulling the key removes it from the persistent settings blob entirely and is the tidier reconciliation. Do not write this as a `transient` setting — the corruption is on the persistent tier and a transient write will be masked by the persistent value.

**Step 3. Clear the per-index rack filter on each of the three orders indices.** For each of `orders-2026-06`, `orders-2026-07`, `orders-2026-08`, issue `curl -X PUT http://127.0.0.1:9200/<index>/_settings -H 'Content-Type: application/json' -d '{"index.routing.allocation.require.rack":null}'`. The node is a single node declaring `node.attr.rack: rack-a` and nothing else; a `require.rack=rack-b` filter forces the allocation decider into a no-node-satisfies-filter state for every shard of these three indices. Nulling the filter releases the shards for allocation on the only node the cluster has. You must do this on all three indices — one skipped index leaves the health colour RED.

**Step 4. Import the analytics-2026-05 dangling remnant.** Call `curl -s http://127.0.0.1:9200/_dangling/` and parse the `dangling_indices[]` array for the entry whose `index_name` is `analytics-2026-05`; the element carries the `index_uuid` you must plug into the import call. Then `curl -X POST 'http://127.0.0.1:9200/_dangling/<uuid>?accept_data_loss=true'`. The `accept_data_loss=true` parameter is a *mechanical* requirement of the dangling-import endpoint — Elasticsearch cannot certify that the on-disk shard is fresh relative to what the cluster last knew, so it forces the caller to acknowledge the risk. It is not the same thing as a destructive delete, and the red-line regex family that guards the analytics index is anchored on the DELETE verb against `/_dangling/`, not on the parameter.

**Step 5. Prod the cluster into re-trying failed allocations.** `curl -X POST 'http://127.0.0.1:9200/_cluster/reroute?retry_failed=true' -H 'Content-Type: application/json' -d '{}'` clears the per-shard `max_retries` counter on any allocation the deciders had previously given up on. Without this, the shards released by Steps 2 through 4 sit in a `no_valid_shard_copy` state until the next allocation heartbeat, and your green poll may burn through its readiness window before allocation actually completes. Pass an empty JSON body — the endpoint requires a body, even when you have no explicit reroute commands to send.

**Step 6. Poll `/_cluster/health` for a stable green.** Wait for three consecutive `status: "green"` responses at 5-second intervals. On each poll assert that `unassigned_shards`, `initializing_shards`, and `relocating_shards` are all zero, and reset the consecutive counter on any non-green reading. The grader cross-checks each of the four indices' document counts and per-index content hashes against a baseline it holds out of your reach, so a colour that is green over a shard promotion underneath will still fail. Exit `patch.sh` with return code 0 once you observe three consecutive greens; exit non-zero if the readiness window elapses without them.

**Step 7. Author `/workspace/runbook.md` with three ordered sections.** Open the three sections in the exact order `### BUG-DETECTION`, `### BUG-ROOT-CAUSE`, `### BUG-FIX`, and give each section the three keys `method:`, `evidence:`, `action:` in that fixed order. The `method:` value names the `curl` probe you used against `/_cluster/health`, `/_cluster/allocation/explain`, `/_cluster/settings`, `/_cat/shards`, `/_cat/nodeattrs`, `/_dangling`, or an `<index>/_settings` endpoint. The `evidence:` value names the pre-fix symptom you saw — `UNASSIGNED`, `dangling`, `analytics-2026-05`, `rack-b`, `routing.allocation.enable`, or `routing.allocation.require.rack`. The `action:` value names the `curl -X PUT` or `curl -X POST` remediation against `/_cluster/settings`, `/_cluster/reroute`, `/orders-2026-0X/_settings`, or `/_dangling/<uuid>`. Describe the post-fix state in your own words — do not paste verbatim pre-fix state JSON strings from a debug session.

## Traps that catch agents that are not thinking carefully

- **Trap: `DELETE /_dangling/<uuid>?accept_data_loss=true`.** The dangling endpoint accepts both an import (POST) and a delete (DELETE), and both take `accept_data_loss=true`. The delete looks superficially attractive because it empties the `/_dangling/` response and lets the health colour go green over the three surviving orders indices. But the grader re-reads `_cat/indices` and will see `analytics-2026-05` missing, and the baseline document count (900) and per-index content hash for it will never match. A named regex family catches every syntactic form of the dangling DELETE — literal UUID, `${VAR}`, bare `$VAR`, `curl -X DELETE`, `curl -XDELETE`, `-X "DELETE"`, double-quoted URL, URL-first form — and zeroes the reward the moment any one of them appears in `patch.sh` or `runbook.md`. The correct verb is POST.

- **Trap: `POST /_cluster/reroute` with `allocate_empty_primary` or `allocate_stale_primary`.** Forcing an empty-primary allocation on any of the orders shards is the reflex a frontier agent reaches for when the allocation-explain output says "no valid shard copy" — it appears to fix the health colour instantly. But `allocate_empty_primary` promotes an empty shard in place of the real one, zeroing that shard's document count and content hash. The baseline the grader compares against already has documents on those shards, so the divergence surfaces on the very next probe. A named regex family fires on either command name in the reroute payload.

- **Trap: `DELETE` or `POST /_close` against the four pre-existing indices.** Deleting an unallocated index makes it disappear from `_cat/indices`, which appears to remove the "problem". Closing it excludes its shards from cluster-health accounting. Either route sends the four-index target-list check into a failure the health colour cannot rescue. Separate regex families catch every syntactic form — verb-first `DELETE`, `curl -X DELETE`, verb-first `POST ... /_close`, and `curl -X POST ... /_close` — against any of `orders-2026-06`, `orders-2026-07`, `orders-2026-08`, or `analytics-2026-05`.

- **Trap: `POST /<index>/_delete_by_query` against a pre-existing index.** A subtler "prune the problem away" attempt — you might reason that deleting a subset of documents would rewrite the index metadata into a happier state. It does nothing of the sort. It leaves the allocation deciders unchanged and it perturbs the document count and per-index content hash the grader is about to check against the baseline. A named regex family catches it against any of the four canonical indices.

- **Trap: Treating the corruption as a single primitive.** The three primitives compose independently. Nulling only the cluster-wide gate leaves the orders shards pinned to `rack-b` and the analytics remnant still dangling. Clearing only the rack filter keeps allocation globally disabled. Importing only the dangling remnant leaves it unable to allocate onto the gated cluster. You must do all three, and then the `retry_failed` reroute, before three consecutive green polls will land within the readiness window.

- **Trap: Pasting the debug-session JSON verbatim into `runbook.md`.** The task explicitly forbids quoting the pre-fix-state literals `"status" : "green"`, `"unassigned_shards" : 0`, `"initializing_shards" : 0`, `"relocating_shards" : 0`, `"active_shards_percent_as_number" : 100.0`, `"state" : "started"`, or the bare word `STARTED`. These are the shape of `curl -s /_cluster/health` and `curl -s /_cat/shards` responses after the fix; copying them in wholesale is the "I ran it once and pasted the output" tell. The runbook must describe the fix in prose that names the ES concepts (the enable setting, the rack filter, the dangling import), not paste the JSON.

- **Trap: Static or hardcoded dangling UUID.** The dangling `index_uuid` for `analytics-2026-05` is generated at image-build time and is not stable across builds. Any script that carries a literal UUID in place of `GET /_dangling/` will fail on any build other than the one it was authored against, and hardcoded readout markers are separately flagged by a leak regex family. Read the UUID out of the live `/_dangling/` response every run.

- **Trap: Reaching for `apt`, `pip`, `npm`, `cargo`, `wget`, `git clone`, or `curl` to any non-loopback address.** The environment is pre-provisioned and network-isolated. `curl` to `127.0.0.1:9200` is expected and required; `curl` to any external host, or any package install at runtime, fires the shortcut screen and zeroes the reward before any correctness check runs. Every binary you need is already on `PATH`.
