# Reconcile a compound PgBouncer + Redis drift against a Postgres backend under 50-worker replay

## The single most important insight

You are looking at three faults that are structurally independent but interact ferociously under the pinned 50-worker replay: `/etc/pgbouncer/pgbouncer.ini` carries `pool_mode = transaction` even though the Python worker uses `psycopg2` with its default server-side prepared statements (`PSYCOPG2_PREPARE_THRESHOLD = 5`); `/etc/app/config.py` holds `CACHE_LOCK_TTL_SECONDS = 1` for a Redis `SETNX`-based cache-fill mutex that must survive a 2-to-5-second catalog `SELECT`; and `max_client_conn = 20` caps the PgBouncer accept queue at less than half the pinned worker fan-out. Fixing any one primitive leaves the other two firing. The lever this task turns on is refusing to reason locally: a naive triage that "fixes the currently loudest log line" chases a moving symptom stream, and each iteration burns close to the 180-second worker ceiling before surfacing the next primitive.

The subtler lever is that two of the three primitives live in a config file that PgBouncer only re-reads on `supervisorctl restart pgbouncer` or `pkill -HUP pgbouncer`. Editing `pgbouncer.ini` without reloading the process leaves the live PgBouncer routing on the old settings; a `grep` against the config file passes and yet the ABSENCE checks on `prepared statement "..." does not exist` and `login timeout` still fire because the actual behaviour has not moved. The reload is load-bearing, and skipping it is the single most common reason an otherwise-correct patch fails grading.

## The ideal solve, step by step

**Step 1. Read all three log streams before touching anything.**

Tail `/var/log/postgresql/postgresql-16-main.log` for `prepared statement "..." does not exist` lines, `/var/log/pgbouncer/pgbouncer.log` for `login timeout` lines, and the worker stderr from a probe invocation for `stampede detected` lines. Each line class identifies exactly one primitive: prepared-statement misses point at PgBouncer transaction-pool mode against psycopg2's default `PSYCOPG2_PREPARE_THRESHOLD`; login timeouts point at `max_client_conn` less than the pinned worker fan-out; stampede lines point at a Redis `SETNX` mutex whose TTL expires mid-fill. Reading only the loudest log and single-fixing that symptom is what makes this task expensive — every diagnose-fix-replay loop consumes the 180-second ceiling.

**Step 2. Confirm every primitive against its config file.**

Run `grep -E '^(pool_mode|max_client_conn)' /etc/pgbouncer/pgbouncer.ini` and `grep CACHE_LOCK_TTL_SECONDS /etc/app/config.py`. You will see `pool_mode = transaction`, `max_client_conn = 20`, and `CACHE_LOCK_TTL_SECONDS = 1`. The three baseline values against which you must reconcile are `pool_mode = session`, `max_client_conn >= 50` (reference 100, which admits retry and admin-session headroom), and `CACHE_LOCK_TTL_SECONDS >= 30` (reference 30, sitting above the 2-to-5-second catalog-fill ceiling). Grounding the diagnosis in the config-file bytes — not the current log line — is what separates a diagnosis from a symptom chase.

**Step 3. Also probe the live composition via the admin interfaces.**

Run `psql -h 127.0.0.1 -p 6432 -U pgbouncer -d pgbouncer -tAc 'SHOW POOLS'` to see the live pool_mode column, `psql -h 127.0.0.1 -p 6432 -U pgbouncer -d pgbouncer -tAc 'SHOW CONFIG'` to confirm the live `max_client_conn`, `redis-cli -p 6379 INFO clients` for the Redis-side connection posture, and `supervisorctl status postgres pgbouncer redis` to confirm the three services are RUNNING under supervisord. These probes are what your `runbook.md` `method:` lines should describe; a runbook that never named a live-composition probe is a hindsight recital, not a diagnosis.

**Step 4. Author `/workspace/patch.sh` as three sed edits, one reload, and a bounded readiness poll.**

In order: `sed -i 's/^pool_mode\s*=\s*transaction/pool_mode = session/' /etc/pgbouncer/pgbouncer.ini`, then `sed -i 's/^max_client_conn\s*=\s*20/max_client_conn = 100/' /etc/pgbouncer/pgbouncer.ini`, then `sed -i 's/^CACHE_LOCK_TTL_SECONDS\s*=\s*1/CACHE_LOCK_TTL_SECONDS = 30/' /etc/app/config.py`, then `supervisorctl restart pgbouncer`, then a loop polling `psql -h 127.0.0.1 -p 6432 -U pgbouncer -d pgbouncer -tAc 'SHOW POOLS'` at 2-second intervals for up to 30 seconds until the query returns without error and the pool_mode column reads `session`. Then `exit 0`. The reload is load-bearing: without it the two `pgbouncer.ini` edits are inert. `pkill -HUP pgbouncer` is an accepted alternative to `supervisorctl restart pgbouncer`, but the supervisord-driven restart is more robust in this composition because it re-invokes pgbouncer with its uid mapping intact.

**Step 5. Author `/workspace/runbook.md` in the pinned three-section schema.**

Three H3 headings in the fixed order `### BUG-DETECTION`, `### BUG-ROOT-CAUSE`, `### BUG-FIX`. Each section carries three key-value lines in the pinned order `method:`, `evidence:`, `action:`. Under `method:`, name the probe you ran (`psql` over 5432 and 6432, `redis-cli` over 6379, `supervisorctl status`, `grep` over the three log paths, `SHOW POOLS`, `SHOW CONFIG`, `INFO clients`). Under `evidence:`, name the concept you observed (`pool_mode`, `max_client_conn`, `CACHE_LOCK_TTL_SECONDS`, `PSYCOPG2_PREPARE_THRESHOLD`, `SETNX`, `prepared statement`, `login timeout`, `stampede`, `session mode`, `transaction mode`) — the concept, never the verbatim pre-fix log literal or the seeded value. Under `action:`, name the reconciliation step (`sed -i`, `supervisorctl restart`, `pkill -HUP`, `SET NX EX`, `SETEX`). Post-fix reconciliation actions belong here; a debug-session transcript does not.

**Step 6. Verify against the live composition before declaring done.**

Run `python3 /opt/app/worker.py --replay --requests 1000 --workers 50 --seed 42` from `/workspace/` and confirm: exit code 0, `replay_ok=true` on stdout, zero `Traceback` and zero `psycopg2.errors` in stderr, `requests`/`catalog`/`audit` row counts of 1000/5000/1000, zero `prepared statement "..." does not exist` lines newly appended to the Postgres log, zero `login timeout` lines newly appended to the PgBouncer log, zero `stampede detected` lines in worker stderr, and `SHOW POOLS` reporting `pool_mode = session` across all pools. If any check fires, the primitive it points to has not actually been reconciled — the first thing to check is that pgbouncer was reloaded, not just that pgbouncer.ini was edited.

## Traps that catch agents that are not thinking carefully

- **Trap: Editing `pgbouncer.ini` without reloading the process.** `sed -i` mutates the file on disk, but PgBouncer only re-reads its config on SIGHUP or a supervisord restart. A patch that edits `pool_mode` and `max_client_conn` but omits `supervisorctl restart pgbouncer` (or `pkill -HUP pgbouncer`) leaves the live PgBouncer routing on the old transaction-pool 20-client-cap settings. The `grep` on the config file passes; the actual behaviour does not change; the ABSENCE checks on `prepared statement "..." does not exist` and `login timeout` still fire. This is the single most common failure mode on an otherwise-correct patch and is not visible from static inspection of the config file alone.

- **Trap: Silently removing the Redis `SETNX` cache-fill mutex to "fix" the stampede symptom.** The reflexive response to `stampede detected` in worker stderr is to delete the lock code that raised the warning. That path is explicitly forbidden and is regex-rejected: `sed -i '/SETNX/d' /opt/app/worker.py`, `python3 -c 're.sub(...setnx...)'`, `cat > /opt/app/worker.py <<EOF` heredoc rewrites without `SETNX`, and comment-line documentation of the removal (`# removed the SETNX cache-fill mutex`, `# no longer using stampede mutex`) all fire. The correct fix is to raise `CACHE_LOCK_TTL_SECONDS` above the 2-to-5-second catalog-fill ceiling (or to atomicize the `SETNX`+`EXPIRE` pair into a single `SET key value NX EX ttl` call while preserving mutex semantics). Removing the mutex leaves cache-fill unguarded and will re-stampede on every warm-cache miss under production load.

- **Trap: Repointing the worker to Postgres 5432, bypassing PgBouncer entirely.** Faced with prepared-statement errors from a pooler, the shortcut is to point `psycopg2` at Postgres directly and eliminate the pool. That path is regex-rejected: `POSTGRES_PORT = 5432`, `POSTGRES_HOST = 127.0.0.1` with an inline `5432`, or `psycopg2.connect(port=5432)` all fire. The task is a PgBouncer composition; the fix is to make PgBouncer's `pool_mode` compatible with `psycopg2`'s server-side prepared statements (or to set `PSYCOPG2_PREPARE_THRESHOLD = None` so `psycopg2` stops issuing them), never to remove PgBouncer from the path.

- **Trap: Reducing `WORKER_CONCURRENCY` below 50 to "fit within" the corrupted `max_client_conn = 20` cap.** The shortcut when `pgbouncer.log` shows `login timeout` is to shrink the worker fan-out until the queue no longer overflows. That path is regex-rejected (`WORKER_CONCURRENCY = <n<50>`, `--workers <n<50>`) and would fail the verifier anyway — the verifier pins `--workers 50` on the invocation line, overriding any config change. Raise `max_client_conn` to admit the pinned fan-out; do not shrink the fan-out to fit an undersized pool.

- **Trap: Pasting verbatim pre-fix log literals into `runbook.md`.** A tidy-looking runbook that quotes the exact strings from a debug session — `prepared statement "S_1" does not exist`, `psycopg2.errors.InvalidSqlStatementName`, `login timeout`, `stampede detected`, `pool_mode = transaction`, `CACHE_LOCK_TTL_SECONDS = 1`, `max_client_conn = 20` — triggers the forbidden-pre-fix-literal guard. Describe the concept and the probe (`prepared statement`, `login timeout`, `stampede`, `pool_mode`, `CACHE_LOCK_TTL_SECONDS`, `max_client_conn` as terms; `psql SHOW POOLS`, `grep ... /var/log/pgbouncer/pgbouncer.log`, `redis-cli INFO clients` as probes) — never the raw pre-fix state values or the exact log lines.

- **Trap: Fixing only the loudest symptom and re-running.** Prepared-statement errors are the most visible in a fresh replay, so a naive triage fixes `pool_mode` first, restarts pgbouncer, re-runs the replay, hits `login timeout`, fixes `max_client_conn`, restarts, re-runs, hits `stampede detected`, fixes `CACHE_LOCK_TTL_SECONDS`. Each iteration burns close to the 180-second worker ceiling and the whole compound diagnosis eats real budget. Diagnose all three primitives from the log streams and config files first, then apply the whole patch in one shot with a single pgbouncer reload — the reasoning surface is compound, so the fix must be too.

- **Trap: `redis-cli FLUSHALL` (or `FLUSHDB`) to "clear the poisoned stampede state" before re-running.** The shortcut when the Redis lock feels contaminated is to flush the keyspace and start clean. That path is regex-rejected in both the invocation form (`redis-cli FLUSHALL`, `redis-cli -p 6379 FLUSHDB`) and the bare-verb form (`FLUSHALL`, `FLUSHDB` case-insensitive). No flush is needed: the Redis lock key is cleared naturally by the worker's per-replay initialization path, and the primitive is a TTL misconfiguration, not a leftover key value.

- **Trap: `DROP TABLE` or `TRUNCATE` on `requests`/`catalog`/`audit` to "reset" the state.** The three pre-existing tables must stay intact: `catalog` holds a 5000-row deterministic-seed baseline whose SHA-256 content hash is verified against a private baseline captured at image-build time, and `requests`/`audit` must be reachable for the worker replay to populate to 1000 rows each. `DROP TABLE (IF EXISTS)? (requests|catalog|audit)`, `TRUNCATE (TABLE)? (requests|catalog|audit)`, and `psql -c 'DROP ...'` variants are all regex-rejected. The fix is a config edit, not a data mutation.
